## 0. 一句话全局

本项目是一个**功能完备的纯前端装修记账 PWA**（6094 行核心代码，35 次提交，功能对标商业 App「装修工地」），
**不是**安卓原生工程。做成安卓 APP 的最佳路径是 **Capacitor 壳打包**（已在本机验证可编译出 APK），
而非 Kotlin 重写。现有资产复用率约 **90%**——数据模型、UI、图表、业务逻辑全部保留，
只有「浏览器 API → 原生能力」这一层需要替换。

| 资料 | 作用 | Android 化复用方式 |

| `app/scripts/probe/probe.js` | 窄屏探针：9 状态交互 + 溢出审计 + 数值勾稽 | **直接复用**；Android 端可考虑用 WebView 远程调试接同一套断言 |

> 固定 `wait()` 会读到上一次渲染的 DOM（假象）。探针必须用「等 DOM 稳定」而非固定等待。

## 4. 技术选型结论（本机实证，非纸面推演）

### 路线对比

| 维度 | **路线 A：Capacitor 壳** ✅ 选定 | 路线 B：Kotlin/Compose 原生重写 |
|---|---|---|
| 现有代码复用 | **~90%**（6094 行基本全留） | ~10%（只有数据模型与需求可参考） |
| 开发工作量 | **2.5~4 周**（含真机调试与发布） | 12~20 周 |
| 风险 | 低（WebView 行为与浏览器一致，已验证） | 高（UI 全重画，易漏功能） |
| 视觉一致性 | 完美（同一份 CSS） | 需重做全部样式 |
| 原生能力 | 官方插件覆盖通知/相机/分享/剪贴板 | 直接写原生，最自由 |
| 后续维护 | 需同时懂 Web 与少量 Kotlin | 纯 Kotlin，门槛单一 |
| 包体 | ~4MB（实测） | 5~8MB |
| 性能 | 满足记账场景（数据量小、渲染轻） | 略优 |

**选定路线 A**。装修记账是**表单驱动、数据量小、无重型动画**的应用，WebView 完全够用；
真正需要原生的只有通知与相机，而这正是 Capacitor 插件最成熟的两个领域。

**关键依赖**：

- `sw.js` + `manifest` 是 PWA 专属，Android 化后**废弃**，但其职责（离线缓存、通知）要由原生接管。
- `DESIGN_TOKENS.md` 与 `verify.js` 是**跨形态资产**——不管最终是 PWA 还是 APK，样式规范与门禁都继续有效。
- `memory/` + git 是**决策档案**——重构时判断「为什么这么设计」的唯一依据。
- `probe/` 是**质量保障**——Android 端 WebView 内的行为仍需这套断言兜底。

## 7. 给后续工作的三条硬约束

1. **不要在 Android 化过程中重写业务逻辑**。`app.js` 的 4546 行是资产不是负债；只有 8 类浏览器 API 的调用点需要替换。
2. **不要丢掉回归基建**。`verify.js` 与 `probe/` 在 Android 阶段的价值更高（原生壳容易掩盖 Web 层回归）。
3. **口径要写进界面文案**。统计双口径、预测只算已录入节点、周期待确认才入账——这三条用户都容易误解，
   Android 版同样要在 UI 上明说，否则客服问题会重复出现。
