## 0. 目标与非目标

**目标**
1. 把现有 PWA 变成可安装、可上架、可长期维护的安卓 APP「工账」；
2. **功能 1:1 不减**（竞品参考图全部需求 + 本项目 10 项增强，见摘要 §4）；
3. 补齐"原生 App 该有而网页没有"的能力：系统通知（到点即弹）、原生相机、物理返回键、分享、权限与状态栏；
4. 数据必须比网页版**更不容易丢**。

**非目标**
- 不用 Kotlin/Compose 重写 UI（复用率会从 90% 掉到 10%，工期从 3~4 周涨到 12~20 周）；
- 不引入账号体系与云同步（保持纯本地，隐私声明最简、审核阻力最小）；
- 不在本轮改动业务口径（双口径、预测、周期记账口径一律照搬）。

## 1. 技术选型

### 1.1 路线结论

| 维度 | **路线 A：Capacitor 壳（选定）** | 路线 B：Kotlin/Compose 重写 |
|---|---|---|
| 现有代码复用 | **≈90%**（6094 行基本全留） | ≈10%（只有数据模型可参考） |
| 工作量 | **3~4 周** | 12~20 周 |
| 视觉一致性 | 完美（同一份 CSS / Token） | 全部重做 |
| 风险 | 低（WebView 行为与浏览器一致） | 高（已验证功能极易漏） |
| 包体 | ~4MB（debug 实测） | 5~8MB |
| 后续维护 | 需同时懂 Web 与少量 Kotlin | 纯 Kotlin |

**选型理由**：装修记账是**表单驱动、单机几千条数据、无重型动画**的应用，WebView 性能绰绰有余；
真正需要原生的只有**通知**与**相机**，而这两个恰是 Capacitor 生态最成熟的插件。

### 2.3 架构关键决策：先建抽象层，再接插件

```
js/bridge.js
  ├─ isNative()            能力探测：是否在 Capacitor 环境
  ├─ Bridge.notify()       → LocalNotifications   |  Notification+SW
  ├─ Bridge.camera()       → Camera               |  input[type=file]
  ├─ Bridge.share()        → Share                |  navigator.share
  ├─ Bridge.clipboard()    → Clipboard            |  clipboard/execCommand
  ├─ Bridge.back()         → App.addListener      |  history
  └─ Bridge.filesystem()   → Filesystem           |  Blob
```

`app.js` 的调用点统一改成 `Bridge.xxx()`。**收益**：
① PWA 形态不被抛弃（用户可能仍用网页版）；② 未来换框架不用再改业务层；③ 改一处两形态同步。

## 4. 数据存储与迁移策略

### 4.1 存储决策

| 方案 | 结论 |
|---|---|
| **保留 IndexedDB** | ✅ **选定（短期 + 中期）**。WebView 的 IndexedDB 落在 App 私有目录，**随 App 数据持久化，不像浏览器会被"清理缓存"误删**——这是升级为 APP 的直接收益之一。改造成本 = 0。 |
| 迁 SQLite | ❌ 本轮不做。理由：数据量小（单机几千条）、现有 8 仓库全部索引齐全、迁移需写数据校验与回滚，风险 > 收益。列为 P2 观察项（若压测发现 >5000 笔时统计页卡顿再启动）。 |
| 附件迁 Filesystem | P2。当前存 IndexedDB Blob，快照已有"12MB 超限时丢附件保主体"的兜底；若用户反馈凭证量大再迁。 |

**必须做的两件事**：
1. 阶段 D 实测「卸载重装是否保留」（Android 默认保留，除非用户主动清数据）；
2. 「我的 → 数据安全」保留并**强化** JSON 导出/导入入口（已有功能，零开发）。

### 4.2 老用户数据迁移路径（PWA → APP）

现有 `exportAll` / `importAll` **已经支持全量备份恢复**（schema 1，附件 base64 内联），因此迁移**零开发**：

```
① 老 PWA 端：我的 → 数据安全 → 导出 JSON 备份
② 传到手机（微信/QQ/USB/邮件均可）
③ 工账 APP：我的 → 数据安全 → 导入备份（内部先存 pre-import 快照，可反悔）
```

配套增强（P1，小工作量）：
- APP 首次启动时，若检测到空账本 → 弹出「从备份恢复 / 从空白开始 / 载入演示数据」三选一向导；
- PWA 网页版首页加一条提示条：「已推出安卓 App『工账』，可在设置中导出备份后导入」；
- 导入结果**明确显示** `{imported, failed}` 条数，失败 ≥1 条时提示"可在回收站/快照回滚"。

### 4.3 品牌改名与标识兼容性（重要）

| 标识 | 现值 | 处理 |
|---|---|---|
| 应用名 / `appName` / `strings.app_name` | 工账 | ✅ 已统一 |
| `appId` / 包名 | `com.gongzhang.app` | ✅ 已统一 |
| IndexedDB 库名 `DB_NAME` | `decor-accounting` | **保持不动**（改名 = 旧数据凭空消失） |
| 备份文件 `app` 字段 | `decor-accounting` | **保持不动**（`importAll` 只校验 `data.stores`，不影响导入；改了反而破坏外部工具兼容性） |

> 结论：**品牌改名只在展示层生效**，存储标识一律沿用，保证向前兼容。

### 4.4 数据安全机制（原样保留，不重造）

| 机制 | 规则 |
|---|---|
| 本地快照 | 保留最近 7 份；>12MB 自动丢弃附件保主体；`restore` 前再存一份 `pre-import` |
| 回收站 | 保留 30 天；项目删除时其流水 + 节点同 `groupId` 一并入站，可整体还原 |
| 自动快照 | 启动时若距上次 >24h 自动存一份（原生阶段改为可周期触发） |
| 演示数据 | 可一键还原演示 / 清空为空白（操作前自动存快照） |

**里程碑 M2「原生能力通」**：不打开 App 到点弹通知；原生相机拍照凭证保存后重开仍在；各级返回键行为正确。

## 6. 需要补充或调整的功能点

### 6.1 必须补（不补就是硬伤）

| # | 功能 | 原因 |
|---|---|---|
| N1 | 物理返回键分级处理 | 网页版不存在；不处理会直接退出 App |
| N2 | 通知预排程 + ROM 白名单引导 | 网页版靠轮询，App 内应做到点即弹；国产 ROM 默认拦后台通知 |
| N3 | 相机权限申请与被拒降级 | 原生相机权限更规范，但也多了"被拒"分支 |
| N4 | 状态栏配色 + 启动闪屏 | 冷启动白闪是最直观的"不像原生 App"信号 |
| N5 | 备份文件落地到手机存储 | Android 11+ 分区存储限制，网页版的 `a[download]` 在 WebView 内不可靠 |
| N6 | 导出/导入的成败反馈与回滚入口 | 导入失败必须有明确条数与回滚路径，否则用户会以为"数据丢了" |

## 8. 需要你确认的事项

| # | 问题 | 备选 | 我的建议 |
|---|---|---|---|
| Q1 | **是否继续维护 PWA 网页版？** | A 双形态并行（bridge 双实现）/ B 只保 App（bridge 只写 Native 实现） | **A**。成本增加约 10%，但保留网页版作为回退与传播入口 |
| Q2 | **最低安卓版本** | minSdk 23（Android 6，覆盖 ~99%）/ 26（Android 8，覆盖 ~97%） | **23**（Capacitor 8 默认起步，无需额外成本） |
| Q3 | **上架渠道** | 仅内测分发（APK 直装）/ 华为+小米+应用宝 / 全部含 Google Play | **先内测分发，跑通后再定商店**。上架涉及软著与隐私合规，周期不可控 |
| Q4 | **是否要应用锁（指纹/密码）** | 要（P3，+2~3 天）/ 不要 | **暂不要**。首版先保证稳定，列为 v3 需求 |
| Q5 | **通知策略** | 预排程（到点即弹，需维护排程同步）/ 沿用轮询（改造小） | **预排程**。收付款提醒是本 App 核心价值，轮询等于没有 |
| Q6 | **附件存储** | 保留 IndexedDB Blob / 迁原生 Filesystem | **保留**。若压测或用户反馈凭证量大再迁 |
| Q7 | **演示数据** | 首启保留演示账本（现状）/ 首启直接进入迁移向导 | **保留演示账本 + 首页可一键清空**，但向导在"检测到空账本"时再出现 |
| Q8 | **阶段 A 是否现在就跑 Gradle 出包** | 立即跑 / 等方案确认后一起跑 | **建议立即跑**。它是唯一能证伪"整条链路是否通"的动作，1~2 天，且不影响方案其余部分 |

## 9. 建议的第一步

**阶段 A（1~2 天）**，产出第一个「工账」APK（不是 hello world）：

1. `node build.js` → `npx cap sync android`；
2. `bash scripts/build-android.sh`（JDK 21 + 腾讯镜像 + `--no-build-cache`）；
3. `adb install -r` 装真机，跑 A3 冒烟四条（不白屏 / 有数据 / 记账拍照 / 杀进程重开数据还在）；
4. `git commit` 把 `android/` 入版本库。

有了这个 APK，阶段 B 之后的所有工作都有可见的验证物。
