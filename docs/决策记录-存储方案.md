# 决策记录（ADR）：安卓端数据存储方案

> 状态：**已决定**（2026-10-31）　|　影响模块：`js/db.js`、`js/bridge.js`、数据安全体系
> 决策人：开发侧　|　复核触发条件：见文末「重新评估的信号」

---

## 背景

工账是从纯前端 PWA 迁移来的 Capacitor 应用。数据在 Web 形态下存 IndexedDB（8 个对象仓库），
迁移到安卓后需要决定：继续用 IndexedDB，还是换成原生存储（SQLite / Filesystem）。

约束条件：
1. 现有 `db.js` 有 479 行、8 个仓库、回收站与快照机制，**改造成本越高风险越大**；
2. 业务量级：单机几千条流水、几十个项目（不是百万级）；
3. 凭证图片存的是 `Blob`，体积是数据主体；
4. 「数据不能丢」是本 App 的生存底线。

---

## 决策

### 结论：保留 IndexedDB，本轮不迁 SQLite

| 方案 | 结论 | 理由 |
|---|---|---|
| **保留 IndexedDB** | ✅ 选定 | 改造成本 0；WebView 的 IndexedDB 落在 **App 私有数据目录**，随 App 持久化，**不会像浏览器那样被「清理缓存」误删**——这本身就是升级为 APP 的收益 |
| 迁 `@capacitor-community/sqlite` | ❌ 本轮不做 | 需要重写 8 个仓库的读写层 + 数据迁移 + 双向校验 + 回滚预案；收益（大数据量性能）在当前量级下不成立；风险远大于收益 |
| 附件迁 `@capacitor/filesystem` | ⏸ 观察 | 当前凭证存 Blob，快照有「>12MB 自动丢弃附件保主体」的兜底；若用户反馈凭证量大再迁 |

### 配套动作（已实施）

1. **备份链路加固**（阶段 C4）：导出走 `Bridge.files.saveAndShare()` —— 写入应用文档目录后
   唤起系统分享面板，用户可存到任意位置或发到微信文件传输助手。
   Android 11+ 分区存储下直接写公共 Downloads 不可靠，交给用户选位置最稳。
2. **导入链路复用**：`<input type=file>` 在 WebView 内会唤起系统文件选择器，导入功能无需原生插件。
   导入前强制存 `pre-import` 快照，坏备份可一键回滚（v2.0.0 已有机制）。
3. **标识保持向前兼容**：`DB_NAME = 'decor-accounting'`、备份文件 `app` 字段同为 `decor-accounting`，
   **一律不改**。品牌改名「工账」只在展示层生效，改了会让旧备份与旧库认不出来。
4. **快照/回收站/去重表**：
   - 快照 7 份、回收站 30 天 —— 原样保留；
   - 通知去重表从 `localStorage['notifyLog']` 沿用（WebView 内可用）；
   - 新增 `localStorage['gzNotifyIds']` 记录本轮已排程的通知 id，用于取消失效排程。

### 必须实测的三件事（阶段 D/E）

| # | 验证项 | 期望 |
|---|---|---|
| 1 | 卸载重装后数据是否保留 | 保留（除非用户主动清数据） |
| 2 | 5000 笔流水 + 200 张凭证下各页耗时 | 首屏/流水/统计/导出均 < 1.5s |
| 3 | 杀进程 / 后台被回收后重开 | 状态与滚动位置恢复正确 |

压测数据生成：`node scripts/gen-stress-data.js 5000 200 out/压测备份.json`，
脚本会打印「预期总余额」，可与 App「我的」页对账。

---

## 重新评估的信号

出现以下任一情况，应重新评估迁 SQLite：
- 实测单机流水 > 2 万笔，且统计页/导出耗时 > 1.5s；
- 用户反馈凭证图片导致快照体积频繁触发「丢弃附件」；
- 需要多端同步或服务端协作（届时引入的不只是存储层，而是整体架构）。
